# D1 的 VPS 備援：研究

需求：Church（`bol-church`）與 Finance（`finance-bol`）兩個 D1 資料庫，在 VPS 上各放一份備援。寫入時兩邊同時寫，讀取優先走 Cloudflare；Cloudflare 的免費額度用完時改用 VPS。

## 結論

1. **最划算的做法是升級 Workers Paid，不是自建 VPS。** 費用都是每月 5 美元左右，但 Paid 方案直接取消每日上限，而且不用改任何程式。
2. 如果仍然要 VPS（例如想在 Cloudflare 以外留一份資料），建議做 **「D1 為主、VPS 為非同步副本、額度用完時切成唯讀」**。
3. **不建議做「雙寫＋讀取自動切換」**。它的工程量與資料分歧的風險，都遠大於它要解決的問題。

## 背景數字

| | 免費方案 | Workers Paid（每帳號每月最低 5 美元） |
|---|---|---|
| D1 讀取列數 | 每天 500 萬 | 每月含 250 億，之後每百萬列 0.001 美元 |
| D1 寫入列數 | 每天 10 萬 | 每月含 5,000 萬，之後每百萬列 1 美元 |
| 額度用完 | **讀和寫都被擋**，直到 UTC 00:00 | 沒有每日上限 |
| Time Travel（時間點還原） | 7 天 | 30 天 |
| KV 寫入 | 每天 1,000 次 | 每月含 100 萬次 |

用量估算：

- **修正前：** 整個帳號每天約 1,300 萬列讀取。其中 Finance 看板的一條查詢就佔了 1,170 萬。
- **修正後（估計值，需要上線後用 `wrangler d1 insights` 確認）：** 每天約 50 萬列，約等於每月 1,500 萬列。這只佔 Paid 方案每月含量的 0.06%，實際上不會產生超額費用。

## 為什麼「雙寫＋讀取切換」很難

1. **額度用完時 D1 連寫入都不接受。** 這段時間的寫入只能進 VPS，等 UTC 00:00 恢復後，還要把 VPS 上的寫入回灌 D1。這等於雙向同步：兩邊都可能改到同一列，必須處理衝突與先後順序。
2. **一邊成功、一邊失敗。** 寫 D1 成功、寫 VPS 逾時（或反過來）之後，兩邊就分歧了。要避免這種情況，需要寫入日誌（outbox）、重送與對帳，而且要做到每一張表。
3. **有些 SQL 在兩邊會算出不同結果。**
   - Church 的 `desktop_downloads`（[migration 0019](../../../Church/migrations/0019_desktop_downloads.sql)）用 `AUTOINCREMENT` 主鍵與 `DEFAULT (datetime('now'))`，兩邊會產生不同的 id 和時間。
   - 其他表大多用 `crypto.randomUUID()`，時間也由程式寫入。這部分沒問題。
4. **呼叫點很多。** Church 有 228 處、Finance 有 104 處 `env.DB.prepare / batch`。可以用一個包裝 D1 介面的轉接層，免去逐一修改，但每一種用法都要能在 VPS 上重現：`batch` 的交易語意、`meta.changes`、`.first()` 等。
5. **Worker 怎麼連到 VPS。**
   - HTTP：最直接，但要在 VPS 上自建 API，並做驗證、TLS 與限流。
   - TCP（`connect()`）或 Hyperdrive：免費方案有每天 10 萬次查詢，但只支援 Postgres / MySQL，SQL 方言跟 SQLite 不同，要改查詢。
   - libSQL 的 `sqld` 伺服器：與 SQLite 相容，Workers 可用 `@libsql/client/web` 連線，但它目前是否仍在積極維護，還沒有確認。
6. **讀取切換到 VPS 時，資料可能是舊的。** 如果複製有延遲，切過去的瞬間就會讀到過期資料。Finance 是帳務資料，這一點特別敏感。

## 方案比較

| | A. 升級 Workers Paid | B. VPS 非同步副本＋唯讀降級 | C. 雙寫＋讀取切換 |
|---|---|---|---|
| 每月成本 | 5 美元 | VPS 約 5 美元（之後可再加 Paid） | VPS 約 5 美元 |
| 改程式 | 不用 | 中等：轉接層、複製、唯讀模式 | 很大：轉接層、outbox、回灌、衝突處理 |
| 額度用完時 | 不會用完 | 網站照常可讀，暫停寫入到 UTC 00:00 | 讀寫都能用（前提是同步正確） |
| 資料分歧風險 | 無 | 低（單向複製，D1 永遠是正本） | 高 |
| Cloudflare 以外的備份 | 沒有（但有 30 天 Time Travel） | 有 | 有 |

## 如果做 B：設計草案

**VPS 端**
- 跑一個小型 HTTP 服務（例如 Node + `better-sqlite3`），提供 `/query` 與 `/batch` 兩個端點。用 Bearer token 驗證，放在 Cloudflare Tunnel 或 HTTPS 後面。
- 資料庫用 SQLite，與 D1 同一種方言，現有 SQL 不必改。

**D1 到 VPS 的複製（單向，D1 永遠是正本）**
- 第一步，最簡單：VPS 每晚用 `wrangler d1 export` 匯出兩個資料庫，再匯入 SQLite。最多可能少一天的資料，但零程式改動。
- 第二步，想縮短延遲時：在轉接層裡，每次寫 D1 成功後，用 `ctx.waitUntil` 把同一句 SQL 與參數送到 VPS。送失敗就記一筆待重送，由每小時的 cron 補送，每晚的匯出負責最後對帳。

**唯讀降級**
- 轉接層包住 `env.DB`：先查 D1，遇到每日額度錯誤（code 7500）時記下「降級到下一個 UTC 00:00」，之後的讀取改走 VPS。
- 降級期間的寫入一律拒絕，回覆友善訊息（例如「系統維護中，請稍後再試」），不寫進 VPS。這樣就永遠不需要回灌與處理衝突。
- 前提是先修好上面第 3 點：`desktop_downloads` 改成由程式產生 id 與時間。

**工作量粗估：** 第一步約半天。轉接層加唯讀降級，大約要兩到三天，含測試。

## 建議的順序

1. 先部署這次的讀取修正，用 `wrangler d1 insights` 觀察幾天，確認每天在 50 萬列左右。
2. 升級 Workers Paid，每日上限的問題就此消失。D1 Time Travel 也從 7 天變成 30 天。
3. 如果還想在 Cloudflare 以外留一份，再做 B 方案的第一步（每晚匯出到 VPS）。只有在確實需要「額度用完網站仍能讀」時，才繼續做唯讀降級。
